# TODOS — TS-Native Codegen + Zod Typing for mthds-js

## Goal

Make `pipe_output` strongly typed end-to-end in TypeScript, with the `.mthds` bundle as the single source of truth. A consumer should be able to write:

```ts
import { ExtractedEntitiesSchema, type ExtractedEntities } from "@/methods/hello/main.types";

const result = await client.executePipeline({
  pipe_code: "extract_entities",
  mthds_contents: [bundle],
  inputs: { text },
  outputSchema: ExtractedEntitiesSchema,
});
// result.output is `ExtractedEntities`, parsed + validated by zod.
```

…and have `methods/hello/main.types.ts` regenerated by `mthds gen methods/hello/main.mthds` whenever the bundle changes.

## Architectural choices (decided)

- **TS-native, semantic re-implementation**: `mthds-js` re-implements in TS the _semantic_ logic of `pipelex/pipelex/core/concepts/structure_generation/` — the mapping from `ConceptStructureBlueprint` field types (text/list/dict/integer/boolean/number/date/concept + choices/required/default) to a typed schema. We do **not** port pipelex's `StructureGenerator` machinery (which builds Pydantic Python source via string-concat + `exec()`). The TS path is direct: `.mthds` → typed IR → JSON Schema → zod expression tree → `.ts` source. The pipelex code is the spec to match, not the architecture to copy.
- **Pipeline shape (one path, not two)**: `.mthds` → IR → **JSON Schema** → zod tree → emitted `.ts`. JSON Schema is a real intermediate in the runtime codegen path, not a parallel test-only artifact. Going through it (rather than IR → zod directly) means the same code path that produces zod also produces the artifact we diff against pipelex — no dead code, no drift between "what we ship" and "what we test".
- **What ends up in the generated `.ts` file**: only `import { z } from "zod"`, the per-Concept schemas, the `z.infer`'d types, and the `Schemas` map. **No embedded JSON Schema** — it would bloat the file with no consumer benefit.
- **Where JSON Schema _is_ exposed**: the `mthds schema <bundle> --concept <name>` CLI subcommand prints JSON Schema to stdout. This is what `cli-harness` diffs against pipelex's `model_json_schema()` output. The same internal function feeds both `mthds gen` (→ zod) and `mthds schema` (→ JSON), so conformance covers the runtime path.
- **Zod is a peer dep of `mthds-js`**. Generated files import `zod` from the consumer's `node_modules`. Starter doesn't depend on zod directly.
- **Bulk of work is in `mthds-js`** on the existing `feature/PipeOutput-Typing` branch (based on `release/v0.6.0`). `pipelex` Python gets zero changes. `pipelex-starter-js` only consumes the new SDK surface.
- **TDD throughout.** Each phase: port pipelex fixtures and capture goldens → write failing tests → implement until green.

## Repos touched

- `mthds-js/` — all new code (bundle IR, schema derivation, zod codegen, CLI command, SDK generic, runtime parser).
- `pipelex/` — read-only; we mine fixtures and run a one-off script to capture JSON Schema goldens.
- `pipelex-starter-js/` — consumes the new SDK; the hand-rolled `parseEntities()` narrower goes away.
- `cli-harness/` — adds a conformance test that runs the same fixtures through both pipelex and mthds-js and asserts schema equality.

## Decisions (locked in)

- **Branch**: work on `mthds-js` `feature/PipeOutput-Typing` (already created off `release/v0.6.0`).
- **JSON Schema dialect**: Draft 2020-12, matching Pydantic's `model_json_schema()` default. (Note: `pipelex/language/mthds_schema_generator.py` emits Draft 4 — that's for the _language_ TOML schema for Taplo, not for Concept Stuff structures. Different concern, unrelated to this work.)
- **Strictness**: default zod object behavior (silently strip unknown keys) — matches Pydantic's default `extra="ignore"`. No `.strict()`, no `.passthrough()`.
- **v0 scope**: single bundle. Cross-bundle Concept refs and `refines` are out — see follow-up plans in `./wip/`.
- **Exports**: per-Concept primary (`<ConceptName>Schema` + `type <ConceptName>`), plus a `Schemas` map `{ pipe_code → schema }` for ergonomic lookup at the call site.
- **JSON Schema → zod conversion**: hand-rolled in v0 (no `json-schema-to-zod` dep). Concept structure surface is small; we want full control over generated style.
- **Generated file location**: sibling, `methods/hello/main.types.ts`. Visible, one-path import.

## Phase 1 — Spec capture (mthds-js)

Capture the Concept structure grammar in TS so the rest of the work has a single typed surface. **What we port**: the _semantics_ — field types, cross-field validation rules, what `model_json_schema()` would produce. **What we don't port**: pipelex's `StructureGenerator` machinery (Pydantic source string-building + `exec()`); we don't need an intermediate Python class.

- [ ] Read `pipelex/pipelex/core/concepts/concept_structure_blueprint.py` end-to-end. Note every field, every cross-field validation, every supported `type`.
- [ ] Read `pipelex/pipelex/core/concepts/structure_generation/generator.py` to understand how each `ConceptStructureBlueprint` field maps to a Pydantic field — that mapping is the spec for our IR → JSON Schema step (Phase 4). Skip the source-emission/`exec()` parts.
- [ ] Create `mthds-js/src/concepts/structureBlueprint.ts` with:
  - `ConceptStructureFieldType` union: `"text" | "list" | "dict" | "integer" | "boolean" | "number" | "date" | "concept"`.
  - `ConceptStructureField` interface mirroring `ConceptStructureBlueprint` (description, required, default_value, item_type, key_type, value_type, concept_ref, item_concept_ref, choices).
  - A `parseStructureField(raw: unknown): ConceptStructureField` validator (zod-based) that enforces every cross-field rule pipelex enforces (e.g., LIST requires `item_type`; CONCEPT cannot have `default_value`; `choices` is mutually exclusive with `type` for Literal-only fields).
- [ ] Add inline JSDoc citing the pipelex source line for each cross-field rule (so future drift is traceable).
- [ ] Test: port the _invalid blueprint_ tests from `pipelex/tests/unit/pipelex/core/concepts/structure_generation/` — every case that pipelex rejects, mthds-js must reject with a structurally similar error.

## Phase 4 — IR → JSON Schema (mthds-js)

The conformance gate **and** the first step of the runtime codegen path. Phase 5 consumes this output to build the zod tree. Output must equal pipelex's `model_json_schema()` for the fixture set (modulo deterministic key ordering). Target dialect: **Draft 2020-12**.

- [ ] **Tests first** — `mthds-js/tests/unit/concepts/toJsonSchema.test.ts`:
  - For each fixture, `toJsonSchema(bundleIR, conceptName)` must equal the captured golden JSON.
  - Use a deep-equal that's order-insensitive for object keys but order-_sensitive_ for `required` arrays and array elements.
  - Add a snapshot fallback for the _first_ failure of each shape so debugging is fast.
- [ ] Implement `mthds-js/src/concepts/toJsonSchema.ts`:
  - Map each `ConceptStructureField` to JSON Schema:
    - `text` → `{type: "string"}`
    - `integer` → `{type: "integer"}`
    - `number` → `{type: "number"}`
    - `boolean` → `{type: "boolean"}`
    - `date` → `{type: "string", format: "date"}` (verify against Pydantic golden)
    - `list` → `{type: "array", items: <subschema>}`
    - `dict` → `{type: "object", additionalProperties: <subschema>}`
    - `concept` → `{$ref: "#/$defs/<concept_class_name>"}` with the referenced concept emitted in `$defs`.
    - `choices` → `{enum: [...], type: "string"}` (Pydantic Literal style).
  - Required vs optional: build the Concept's `required: [...]` array from fields where `required: true` AND no `default_value`.
  - Defaults: emit `default` field at the property level.
  - Descriptions: emit `description`.
  - `$defs` collection for nested concept refs.
- [ ] If a golden mismatch is _intentional_ (pipelex emits something we deliberately diverge from), document each divergence in `mthds-js/src/concepts/toJsonSchema.ts` JSDoc with the reason. Default position: **no divergences**.

## Phase 6 — TS file emission (mthds-js)

## Phase 7 — CLI commands `mthds gen` and `mthds schema` (mthds-js)

- `mthds schema <bundle> --concept <name>` → prints JSON Schema for one Concept to stdout. Conformance-facing; used by `cli-harness` to diff against pipelex.

Both call the same internal `bundleToJsonSchema()` from Phase 4, so conformance covers what consumers actually run.

- [ ] **Tests first** — `mthds-js/tests/unit/cli/schema.test.ts`:

## TDD ordering recap

The dependency chain:

- Phase 1 (grammar) → Phase 3 (parse to IR).
- Phase 2 (fixtures + goldens) → Phase 4 (IR → JSON Schema, conformance test).
- Phase 4 → Phase 5 (Schema → Zod) → Phase 6 (emit `.ts`).
- Phase 6 → Phase 7 (CLI).
- Phase 8/9/10 (SDK runtime) can run parallel to 5/6/7 once Phase 4 is green.
- Phase 11 (conformance harness) gates the publish in Phase 14.
- Phase 13 (starter) waits on Phase 12 (mthds-js publish).

**Every phase: tests committed first, implementation in a follow-up commit.** Reviewers (and future-us) get to see the contract land before the code that satisfies it.
