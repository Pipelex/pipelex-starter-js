# Designed pages: a layout a model produced, committed beside the method

This is the reference for the third committed artifact about a method — its **design**, the page a model laid out for it — and for the two gestures around it, `npm run design` and `npm run design:check`. The day-to-day rules live in [`CLAUDE.md`](../CLAUDE.md); the artifact this joins is documented in [`docs/codegen.md`](codegen.md), and the form and result views a design does _not_ replace are in [`docs/input-form.md`](input-form.md).

## Why

Every method in this template already declares what it takes and what it produces, and the app already renders both without a line of hand-written markup: `INPUT_FORM` becomes the form, `OUTPUT_FORM` plus the contract becomes the result view. That is the whole of the shipped behaviour, and it is deliberately generic — one column of controls, in the order the method declares them, for every method there has ever been.

Generic is the right default and a poor ceiling. A real product page has a shape: something above the fold saying what this does, the inputs grouped into steps a person can follow, a rail holding the call to action where the thumb is. None of that is derivable from a contract, because none of it is _in_ a contract — it is a design decision, and until now the only way to have one was to write the page by hand, which is exactly the duplicated surface this template spends its effort removing.

So the arm takes the third option: **a model designs the page once, the layout is committed like any other artifact, and the app renders it.** No inference at request time, no design in the runtime path, nothing to re-derive per visitor. A page is a file in the repository, reviewed in a pull request, and regenerated by a gesture.

The design goal in one sentence: **`npm run design` produces a committed page for a method, `npm run design:check` proves offline that the committed pages still fit their methods and this kernel, and a method that fails either renders the plain form instead.**

## Rule 1: a layout names a path and nothing more

This is the form kernel's own rule, and it is what makes committing a layout safe at all.

A design never says that `text` is required, or that `document` takes a PDF, or that `tone` is one of three choices. It says: _there is a `Textarea` here, bound to `/inputs/text`_. Every fact about the field itself still comes from the descriptor, derived from the method exactly as it is today. Three artifacts, three questions, no overlap:

| Artifact                                                  | Answers                             | Comes from                            |
| --------------------------------------------------------- | ----------------------------------- | ------------------------------------- |
| the **descriptor** (`INPUT_FORM`, `OUTPUT_FORM`)          | what a field _is_                   | the method, through `npm run codegen` |
| the **design** (`design.jsonl`)                           | which path goes _where_ on the page | a model, through `npm run design`     |
| the **state** (the store's `/inputs` and `/result` trees) | what the values _are_ right now     | the person using it                   |

The consequence is the whole point: **a design cannot go stale about a fact it never stated.** Loosen an input's bounds, add a choice, change a description — the page keeps rendering, because none of that was ever in it. Only two things can actually invalidate a layout, and they are precisely the two questions the gates ask: is it written in the vocabulary this kernel renders, and does it still fit this method.

## The artifacts

```
methods/
  extract-entities/
    main.mthds                   # the method
    design.jsonl                 # the layout — json-render patch lines, exactly as emitted
    design.json                  # its provenance, and the hashes the offline gate compares
    design.rejected.jsonl        # a refused layout, when there is one. Gitignored: evidence, not an artifact
src/generated/
  extract-entities/
    design.ts                    # `export const DESIGN: MethodDesign | null` — the projection
    …                            # types.ts, binder.ts, contracts.ts, codegen.lock, sources.json
src/
  lib/design.ts                  # MethodDesign, DesignRecord, acceptDesign, describeFallback
  brand.ts                       # the BrandManifest every designed page renders under
  components/DesignedPage.tsx    # the one composition: the page, its slot, its boundary, its credit
  components/ViewToggle.tsx      # Designed | Plain form — app chrome, beside ModeToggle
  components/DesignFallbackNote.tsx
scripts/
  design.mts                     # CLI entry — npm run design
  design-check.mts               # CLI entry — npm run design:check
  lib/design.mts                 # designMethod, checkMethodDesign, and the pure pieces both use
```

**`design.jsonl` is the layout as the model emitted it, byte for byte.** It is json-render's patch format: one JSON object per line, each an `add` at a path in the spec — `/root`, then `/elements/<id>` for every element. It is never reformatted, never sorted, and **never repaired by hand**; the record beside it signs its SHA-256, so an edit is a failing check rather than a page nobody can trace.

**`design.json` is the provenance**, and it carries two facts the projection deliberately does not: the SHA-256 of every source the method is generated from, and the SHA-256 of the JSONL. Those are what turn "edited the method, forgot to re-design" into a red gate instead of a page that quietly stopped fitting.

```json
{
  "pipeRef": "extract_entities.extract_entities",
  "producer": "pipelex-method",
  "model": "claude-5-sonnet",
  "promptHash": "4dcf6d57cb71",
  "date": "2026-09-06",
  "sources": { "methods/extract-entities/main.mthds": "19e5fc76…" },
  "jsonlSha256": "43a80056…"
}
```

`producer` names **what made the page, never a role** — `pipelex-method` is the designer method the form kernel ships as data. `promptHash` is the first twelve hex digits of the SHA-256 of the catalog prompt the kernel shipped at production time; it is the one field a package bump moves, and the reason it is recorded at all is that a layout is only meaningful in the vocabulary it was written for.

**`design.ts` is the projection, and it is a derived artifact of the codegen tree** — the second one, joining `contracts.ts`. `npm run codegen` writes it for every method: the design when there is one, `null` when there is not. That unconditional projection is what lets a form import `DESIGN` at module level beside `CONTRACT` and `DESCRIPTOR` without knowing whether a page exists. Like `contracts.ts`, it carries no codegen stamp (a stamped file the lock does not track is an orphan, and the writer deletes orphans) and its SHA-256 lives in `sources.json`'s `derived` map instead. See [`docs/codegen.md`](codegen.md#the-contracts-artifact) for why that hole exists and how the sidecar closes it.

## The two commands

| Command                                      | What it does                                                                     | Needs key / network? | Costs inference?                      |
| -------------------------------------------- | -------------------------------------------------------------------------------- | -------------------- | ------------------------------------- |
| `npm run design` / `make design`             | Produce a design for every method that has a generated tree, or one with `NAME=` | Yes                  | **Yes** — one designer run per method |
| `npm run design:check` / `make design-check` | Prove every committed design is current, offline                                 | No                   | No                                    |

`make design` takes `NAME=<method>` to narrow to one, `PIPE=<domain>.<pipe>` on a method that declares several, and `SEED=<text>` to hand the model a creative seed the record then names. `design-check` is in `make check`, so it runs on every `make all`; `design` is out of it for exactly the reasons `codegen` and `test-e2e` are, plus one that outweighs both — **nothing in this repo spends a model call implicitly.**

### Producing one

`designMethod` reads the method's _committed contracts_ rather than the method itself, which is the seam that keeps the producer honest: it renders the brief from the same `INPUT_FORM` the form is rendered from, so the paths a design names are the paths the app will actually hold values at. Then it runs the designer method the kernel ships (`ui_designer`, from `@pipelex/mthds-form/ui-designer.mthds`, resolved through `createRequire`), on the model that bundle pins, with three inputs: the catalog rules, the brief, and the seed when there is one.

What comes back is judged before anything is written, with **the same two functions the runtime gate uses** — `validateAgainstCatalog` and `layoutProblems`. A refusal writes `design.rejected.jsonl` and nothing else: the previous design, if there was one, is still the committed one.

**A refused design is re-run, never repaired.** That rule is not fastidiousness. A layout edited by hand is a layout whose record no longer signs it, so `design:check` fails; and past that, a hand-fixed page is a page the next production will silently undo. If a second run refuses too, the thing to do is file it against `@pipelex/mthds-form` with the problems and the brief — the catalog and the prompt are the package's, and a model that cannot satisfy them twice is telling you something about them.

One failure has its own message because it looks like nothing: an **empty** completion is what a run truncated at the model's output cap looks like on this runtime, so the producer says so rather than reporting an unparseable layout.

### Checking them

`design:check` asks four questions per method, and the last three are asked with the same functions the browser asks them with:

1. **Is the layout the one its record signed?** `sha256(design.jsonl)` against `record.jsonlSha256` — the hand-edit gate.
2. **Has the method moved since?** `record.sources` against the method's current source hashes, the same map `sources.json` records. Editing a bundle without re-designing is a failure here, with the same shape as editing one without regenerating.
3. **Has the catalog prompt moved?** `record.promptHash` against the installed kernel's `PROMPT_HASH` — the package-bump gate.
4. **Does it still compile, validate and fit?** `specFromJsonl`, then `validateAgainstCatalog`, then `layoutProblems` over the fields the contract yields.

Plus one bookkeeping question: does `design.ts` project to what this design projects to, including the `null` case — a tree carrying a design for a method that has none is drift, not a curiosity.

**Exit codes are a contract**, matching `codegen:check`: `0` current, `1` drift, `2` no verdict (half a design on disk — one file without the other — or a missing projection). `make check` fails on `1` and `2` alike.

The point of asking questions 2–4 offline is that **a fallback in the browser is never news the check could have delivered first.** A reviewer sees a red `make check` on the pull request, not a page that quietly went plain in production.

## The fallback rule

A design is a _proposal_. The app renders it when it holds up and renders the kernel's plain form when it does not, and there are five causes:

| Cause          | When                                                                        | Caught by                                |
| -------------- | --------------------------------------------------------------------------- | ---------------------------------------- |
| `none`         | no design has been produced for this method yet — where every method starts | `acceptDesign`                           |
| `prompt_hash`  | produced against a catalog prompt this kernel no longer ships               | `acceptDesign`, and `design:check` first |
| `invalid`      | not written in the vocabulary this kernel renders                           | both                                     |
| `unfit`        | a path it names is gone, or a required input is not offered                 | both                                     |
| `render_error` | the page threw while rendering                                              | `DesignedPage`'s error boundary          |

`acceptDesign(design, fields)` in `src/lib/design.ts` is the runtime gate, and it runs **cheapest first**: the prompt hash is a string comparison against a constant, and it is the condition a package bump moves, so a design produced for an older catalog is refused before anything tries to compile it in a vocabulary that has since changed.

It runs at all — after `design:check` already proved the same things in CI — because **the fallback is the product's safety**, and a template whose fallback path was never taken would be teaching the wrong thing to every reader who copies it. `none` is where every method starts: a bundle you add, or a method `make add-method` scaffolds, renders the plain form until you run the gesture. All five shipped methods have been designed, so each cause is exercised by `src/lib/design.test.ts` rather than by a tab that is permanently plain.

`render_error` is the one cause the gate cannot reach, because it is about rendering rather than about the layout: `DesignedPage` wraps the page in a boundary that reports the message up, and the form swaps to the plain view with the same amber note the others get.

## What a form composes

Every example form is the same shape, and the designed arm added one hook argument and one branch to it:

```tsx
const CONTRACT = requireContract(PIPE_IO_CONTRACTS, "extract_entities", "extract_entities");
const DESCRIPTOR = requireInputForm(INPUT_FORM, "extract_entities", "extract_entities");
const RESULT_FIELD = requireResultField(
  OUTPUT_FORM,
  CONTRACT,
  "extract_entities",
  "extract_entities",
);

const { fields, values, setValues, ready, toData, design, store } = useRunInputs(
  CONTRACT,
  DESCRIPTOR,
  { text: SAMPLE_TEXT },
  DESIGN,
);
```

`useRunInputs` takes the design as its fourth argument, calls `acceptDesign`, and answers with a `DesignVerdict` plus — when the verdict is `ok` — **a json-render store**. That store is the single source of truth for both views: `values`, `setValues`, `ready` and `toData` read it when it exists and React state when it does not, so a value typed on the designed page is on the plain form after a toggle and vice versa, and both views deflate through the same contract to the same wire shape. `ViewToggle` copies nothing, because there is nothing to copy.

Everything else is unchanged. The run path is the same trio of Server Actions, the server-side gate is the same `gateRunInputs` call over the same contract, and a refused run surfaces in the page's own result slot exactly as it does under the plain form. **The fallback rule is about the layout, not about errors** — a run that fails on a designed page is still the designed page's.

That identity is why every shipped method is designed rather than a chosen two: with one store, one gate and one wire behind both views, the toggle isolates the design and nothing else, so a reader can put any method's two renderings side by side and see exactly what a layout adds.

## Where the page's chrome comes from

Two things on a designed page are the template's rather than the model's, and both are deliberate.

**The toggles are app chrome, above the page.** `ModeToggle` and `ViewToggle` sit in a row above the form in _every_ example, designed or not, because the mode toggle has to stay reachable when a designed page is on screen — inside the plain `<form>` it would disappear with it. The PDF example's "Use sample PDF" shortcut moved into the same row for the same reason.

**A designed page takes a full-bleed band.** It renders an app bar, a hero and a two-column workspace with a sticky rail; inside the app's `max-w-2xl` demo column that reads as a phone screenshot of a desktop page. `DesignedPage` breaks out (`mx-[calc(50%-50vw)]`, `overflow-x-clip`) and sets its own measure, leaving the column to the chrome.

It also renders under `FieldPresentationProvider presentation="app"`, the same seam the plain form and the result view use. Without it a field the model **delegates** to the kernel — an `MthdsField`, which is what the `summarize-pdf` layout does with its document input — shows its raw contract name and its concept pill, and the two views disagree about a field neither of them wrote.

Finally, every page carries a one-line credit naming what produced it and when, from the record. A page a model designed should say so.

## The upload seam, and the one id inverse

A file input on a designed page is the only place the host has real work to do, and it is worth understanding because a scaffolded form with a file input inherits it.

The kernel never uploads. Its file control fires `env.onDropFile(id, file)` and waits for the host to write a `FileValue` back at that field's path. On the **plain** form the id _is_ the dotted path. On a **designed** page it is not: `MthdsField` mints the field id from the store pointer it is bound to, so `/inputs/document` becomes `summarize-pdf-inputs-document`. `useFileInputs` therefore takes a `pathOf` mapper, defaulting to `id.split(".")`, and the designed form passes the inverse:

```ts
function inputPathOf(id: string): string[] | undefined {
  const pointer = pathFromDomId(ID_PREFIX, id);
  if (pointer === undefined) return id.split(".");
  return segmentsUnder(INPUTS_ROOT, pointer);
}
```

An id neither form recognises is a **loud** refusal — an inline `bad_request` naming the id — not a silent no-op, because a dropped file that writes nowhere looks exactly like an upload that is still running.

One rough edge, filed upstream (`L-260906-8e4500`): the kernel compares `env.uploadingIds` against the DOM id its own control reported, which additionally carries a React `useId` prefix, and the forward mint is not exported. So a host that wants to hold _one_ designed field busy cannot name it, and `PdfForm`'s sample-PDF shortcut sets `env.disabled` on the whole page for the span of its fetch and encode. Reproducing the mint locally is the drift `pathFromDomId`'s own comment rules out.

## Adding a design to a new method

For a method whose bundle lives here, or one scaffolded by [`make add-method`](add-method.md), the gesture is the same and it is one line:

```
make design NAME=<method>
```

That is the second gesture `make add-method` prints when it finishes. Everything the app needs is already in place before it — the scaffolded tab renders the plain form, which is cause `none` — so producing a design changes which view the tab opens on and nothing else. Commit `methods/<name>/design.{jsonl,json}` together with the re-projected `src/generated/<name>/design.ts` and the updated `sources.json`, and put the provenance in the commit message.

## What is deliberately not built

- **No design at request time.** A page is produced by a gesture and committed. Nothing in `make all`, `make check`, `make codegen` or `make add-method` spends a model call.
- **No hand-repair path.** There is no "fix the layout" flow, and there should not be: a repaired layout fails its own record's signature, and the next production undoes it silently.
- **No half-designed app.** Every shipped method has a page, so every tab carries the Designed | Plain form toggle and a reader can compare the two renderings of any method, not only of a chosen demo. The `none` cause is what a newly added method looks like, and it is covered by the unit tests rather than by leaving a tab plain forever.
- **No per-field design.** A layout is whole-page. Wanting one control moved is a re-run, possibly with a seed — not an edit.
- **No brand yet.** Every page renders under the manifest in `src/brand.ts` and the theme contract the kernel ships. Capturing a brand as data, and building the stylesheet a page reads from it, is its own piece of work.
- **No result design.** `OUTPUT_FORM` still drives the result view, rendered into the page's slot. A model designs how you _ask_; what comes back is still the method's own declaration of what it produces.
