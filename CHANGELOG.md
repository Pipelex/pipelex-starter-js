# Changelog

## [Unreleased]

### Added

- **A plaintext-`http:` guard on the keyed codegen scripts.** `npm run codegen` and `npm run codegen:verify` refuse a `PIPELEX_BASE_URL` using `http:` for any non-loopback host (`localhost`, `*.localhost`, `127.0.0.1`, and `[::1]` stay allowed): the scripts send the API key as a bearer token and write server-supplied TypeScript into the repo, so a non-local plaintext base URL exposes both on the wire.
- **A containment guard on the paths the codegen response names.** `npm run codegen` checks every `artifact.path` before it writes anything and refuses the method whole — nothing written, report it upstream — if one resolves outside that method's tree. The writer had trusted those paths into `path.join`, while `writeIfChanged` creates directories recursively, so a single `..` would have written a file anywhere the process can reach, somewhere no stamp guards it and no check looks. It is the response-side counterpart of the `http:` guard above, which closes the same exposure on the wire.
- **`import "server-only"` in `src/lib/wireOutput.ts`.** A consumer calling a generated `parseXxx` narrower from a `"use client"` component now gets a Next build error instead of silently shipping zod plus every generated schema to the browser; previously the boundary held only because the result components use `import type`. Unit tests alias the package to an empty stub so they keep importing narrowers outside a bundler.
- **Generated types from the `.mthds` bundles.** `npm run codegen` (`make codegen`) sends every method under `methods/` to the API's `/v1/codegen` route and writes what comes back, byte-for-byte, to `src/generated/<method>/`: a `types.ts` of zod schemas with their inferred TypeScript types, a `binder.ts` of `parseXxx` / `serializeXxx` functions over those schemas, and a `codegen.lock`. The trees are committed, so `git clone && make all` still passes without an API key and the diff of a regeneration shows exactly what a bundle edit changed. This replaces the hand-written output shapes the template used to keep in `src/types/` — a duplicate of what each bundle already declares, with nothing to catch the two drifting apart. One caveat while it lasts: `/v1/codegen` is served by any self-hosted `pipelex-api` runner and by `api-dev.pipelex.com`, but `api.pipelex.com` still answers `403` pending its deploy, so regeneration needs `PIPELEX_BASE_URL` pointed at api-dev today. Only regeneration is affected — the offline check needs no server, and the app runs fine against the default hosted URL.
- **An offline drift check, wired into `make check`.** `npm run codegen:check` (`make codegen-check`) re-derives the whole verdict with no key and no network: it verifies each generated tree against its own lock — reporting a hand-edited, missing, or orphaned artifact in the same words the `pipelex` CLI uses — and compares a `sources.json` sidecar of source hashes against the `.mthds` files on disk, so editing a bundle without regenerating fails the build with "Run `npm run codegen` to regenerate." instead of shipping types that quietly lie. It exits `0` when current, `1` on drift or stale sources, and `2` when no verdict could be produced (a missing or malformed lock).
- **A keyed semantic gate.** `npm run codegen:verify` (`make codegen-verify`) re-runs the projection live and compares each method's `crate_fingerprint` against the committed lock's, answering the question the offline check deliberately cannot: whether the committed tree still comes from the crate the method resolves to today. It writes nothing and stays out of `make all`, for the same reason `test-e2e` does — it needs a key and a network. An engine-version difference is reported as a note rather than a failure, since `engine_version` rides in the artifact stamps and a pipelex release restamps every file with no semantic change.
- **`tsconfig.scripts.json`** type-checks `scripts/` the way `tsconfig.e2e.json` type-checks the Playwright specs, and `make typecheck` runs it. The scripts are native-Node TypeScript (`node --experimental-strip-types`), so the template gains no `tsx` or `ts-node` dependency.
- **`AGENTS.md`**, so agents other than Claude Code (Codex, Cursor, Gemini CLI, …) start with the rules that matter — never edit `src/generated/`, regenerate after a bundle edit, `make all` as the done-gate — and a pointer at `CLAUDE.md` for the rest. Next.js's agent-rules block moved into it, since `next dev` prefers an `AGENTS.md` once one exists.
- **A `docs/` directory.** `docs/codegen.md` is the curated design reference for the generated-types workflow (promoted out of internal planning notes), and `docs/adopt-in-an-existing-project.md` is an executable checklist for transplanting the pattern — the codegen scripts, the config that protects the stamps, the server pattern, and the one Next-specific seam (env loading) — into an existing TypeScript app.
- **A "Remove an example" checklist in the README** — the mirror image of "Swap in your own pipeline", listing the full vertical slice a demo owns (bundle, generated tree, loader, adapter, action trio, components, tab entry, e2e spec) so stripping one doesn't have to be assembled from compile errors.

### Changed

- **The shared-helper tests no longer import any example's adapter.** `src/lib/blockingRun.test.ts` and `durableRun.test.ts` used `parseEntities` / `parseGeneratedImage` as their fixture narrowers, coupling the shared layer's tests to demo slices the README calls removable. They now use inline fixture narrowers built on `RunResults` and the shared tagged errors only, so removing an example never touches the shared layer's tests — and the README's removal checklist shrank by that step.
- **Breaking: output field names are wire-native snake_case.** `DocumentSummary` is now `{ title, doc_type, key_points }` (was `docType` / `keyPoints`), and the image envelope carries `public_url`, `mime_type`, and `source_prompt` (was `publicUrl` / `mimeType`). The names travel unchanged from the bundle through the narrower to the components, because the emitter keeps concept keys wire-native and a hand-maintained camelCase mirror is exactly the duplication this release removes.
- **Breaking: `src/lib/runOutput.ts` is gone**, replaced by `src/lib/wireOutput.ts` in the same slot. `findOutputContent`'s predicate search and its non-object guard are subsumed by the generated schema's own `parse`, which rejects arrays, primitives, and `null` with a message naming the failing field — something "not found" could never do. The new module reads `main_stuff`, normalizes it for the schema, and renders a `ZodError` into the readable field-by-field list `<ErrorDisplay>` shows.
- **The narrowers in `src/types/` are now thin adapters over the generated binders.** The `parseXxx(results: RunResults)` contract is unchanged, so actions, `useRun`, the components, and the tests keep their call sites; each narrower's body became "hand the output to the generated binder, translate a `ZodError` into the template's tagged error model". Hand-written validation survives only where it adds semantics the concept does not declare — `parseGeneratedImage` still checks that the URL it is about to render is one a browser can load.
- **A wire-null normalization step, and it is a workaround with an expiry.** The projection emits a non-required concept field as `.optional()`, which in zod means `| undefined` and rejects `null`, while the runtime serializes an unset optional field as an explicit `null`. Verified against a live image run, whose output carries `caption: null` and `filename: null`: without normalization the generated schema rejects the runtime's own payload on every real image run. `dropWireNulls(value, schema)` takes the concept's generated schema and strips a null-valued key only where that schema says a `null` means absence — it descends declared shapes only, so a `null` inside a `z.record()`, a `z.unknown()`, a `.nullable()` field or a `.default()` field is left exactly as the pipeline sent it. A blind deep strip is the one thing the ts-zod emitter's design note rules out, because inside a free-form map a `null` is data and deleting it is silent loss under a green check. It normalizes values and never names, so it re-declares no field, and it is deletable once the emitter emits `.nullish()`. Reported upstream.
- **Bumped `@pipelex/sdk` to `^0.13.0`** (the declared range was `^0.5.1`; the working tree had been running a local `make use-local` tarball of `0.9.0`). No migration was needed in this template for the intervening releases: the only breaking changes are on the methods-catalog surface — `listMethods` now returns one page of `MethodSummary` rows rather than the whole catalog as `MethodData` — and this template never calls it. `0.12.0` added the crate routes `client.resolve()` and `client.codegen()`, and `0.13.0` added `runCodegenCheck`, the pure offline drift check the new `codegen:check` script is built on; between them they are what makes generating these types possible without re-implementing the trust chain here.
- **Added `zod` as a runtime dependency** (`^4.4.3`), not a dev one: the generated binders validate run output inside Server Actions at request time. It costs the dependency tree nothing new — the copy `mthds` already pulls in dedupes with it.
- **`src/generated/` is excluded from Prettier and ESLint, deliberately.** The emitter targets Prettier's defaults (80 columns) while this repo prints at 100, so formatting the generated files would rewrite their bytes and break every stamp. TypeScript still covers them in full, since they live under `src/`.
- **The release and bump-sdk skills now offer `make codegen-verify`** — the release skill whenever a key is configured (it is the documented pre-release gate for the generated types and costs no LLM call), the bump-sdk skill when the SDK changelog touches the codegen surface.
- **`npm run codegen`'s 403/404 message now covers self-hosted runners too**: alongside "point `PIPELEX_BASE_URL` at api-dev" it says to upgrade a self-hosted `pipelex-api` to a version that serves `/v1/codegen` — the right remedy when the base URL is your own runner.
- **The docs no longer offer self-hosting as a supported path.** This template is built on `@pipelex/sdk` to reach the hosted Pipelex API: a bare `pipelex-api` runner has no run store and no file storage, so durable mode and the PDF example cannot work against one — which is why the error layer already recognises that case by name and says so. The prerequisites now say that plainly, and note that dedicated deployments of the hosted plane exist but are not self-serve. The self-hosted arm of `npm run codegen`'s 403/404 message goes with it, and the `PIPELEX_BASE_URL` row now describes an override for another Pipelex endpoint rather than for your own instance. This also settles the contradiction the pre-landing review raised against `assertSecureBaseUrl`'s loopback-only allowlist: there is no supported plaintext non-loopback host to accommodate.
- **Internal planning notes (`wip/`) are untracked again**, as v0.1.1 already decided before open-sourcing — template consumers no longer inherit them, and the codegen design rationale they held now lives in `docs/codegen.md`.

### Fixed

- **The codegen gate could be silently wrong in several ways; each now produces a loud, correct verdict.** A symlink under `methods/` or a generated tree was invisible to the walk — a symlinked `.mthds` dropped out of the codegen closure and the staleness sidecar, so editing it never tripped `stale-source`; symlinks and special files are now refused by name with no verdict — including a symlinked `methods/` or `src/generated/` root, which `lstat` alone cannot catch on child paths. Artifacts were read with lossy UTF-8 decoding, so a corrupted artifact could still hash to its locked value and report `current`; every read is now fatally decoded, mapped as drift in a generated tree and as a refusal in a source. An empty `methods/` exited "nothing to check" before orphan detection ever ran, hiding leftover generated trees; orphans now report first. On a case-insensitive filesystem a tree differing from its method's name in case only was reported as an orphan with a delete remedy — for the very tree the same run had just certified; it now gets a rename remedy. And `REPO_ROOT` was `process.cwd()`, so running a script from anywhere but the package root failed with a raw ENOENT; it now anchors on the script's own location. A failed tree read (permissions, I/O) also no longer collapses into "regenerate": it reports as no-verdict with the underlying message, and a per-category summary line shows the current / drift / no-verdict mix the single exit code cannot. The moved-and-parameterized helpers (`compareSources`, `findOrphanTrees`) are pinned by `mkdtemp`-fixture tests in `scripts/codegenShared.test.mts`.
- **`npm run codegen` deleted hand-written files parked in a generated tree.** The cleanup loop decided what it was allowed to remove with a filename test — `isStampableArtifactPath`, a bare `.ts`/`.py` suffix check — while the SDK's own orphan rule additionally requires the file to _carry a codegen stamp_. The writer and the checker therefore disagreed about what counts as generated, and the disagreement was resolved by deletion: a sibling `augment.ts` was reported by `codegen:check` as a healthy artifact and destroyed by the next regeneration, which is exactly what the generated header tells consumers to write ("Augment it from a sibling module via declaration merging — augmentations survive regeneration"). Cleanup now defers to `runCodegenCheck`'s own `orphan` verdict over the tree it just wrote, so the two agree by construction, and the unlink is `force: true` so a file vanishing mid-loop cannot abort before the sidecar is written.
- **A stray file under `src/generated/` failed the offline check with a remedy naming a directory that does not exist.** Orphan detection derived tree names by walking _files_ and taking each path's first segment, so a `.DS_Store` — which Finder writes into any folder you browse — was reported as `a generated tree with no methods/.DS_Store/ behind it` and exited 1, breaking `make check` and CI on macOS. The mirror bug was that an _empty_ orphan directory contributed no files and was never reported at all. It now reads directory entries directly, which fixes both verdicts and drops a redundant whole-tree traversal.
- **An empty-string `public_url` failed an image run that had a perfectly good `url`.** The narrower this release replaced ran optional strings through a helper that mapped `""` to null; without it, `public_url ?? url` let an empty string win over the real URL, `new URL("")` threw, and `parseGeneratedImage` reported `BadImageOutputError` on a usable image. `<ImageResult>` had the same gap on its `alt` text. Both now use `||`, and the cases are pinned by tests.
- **`codegen:check` reported every method stale on a Windows checkout.** The source hashes behind `sources.json` were taken over the file's raw bytes, while `.gitattributes` pinned only `src/generated/**` — so under `core.autocrlf=true` the `.mthds` files arrive as CRLF, every hash disagrees with the committed one, and the offline check fails with `stale-source` on a tree nobody edited. The remedy it prints, `npm run codegen`, needs an API key and a network the check is defined not to need, and the sidecar that regeneration writes then breaks LF-based CI. `hashSource` now normalizes CRLF and lone CR before hashing, which is the same normalization the SDK's own `runCodegenCheck` already applies to artifacts and to the lock; `methods/**` is pinned in `.gitattributes` alongside it as hygiene. Nothing changes on an LF checkout — normalizing LF is a no-op, so the committed sidecars are byte-identical.
- **A renamed lock file could have left the offline check validating the obsolete one.** `codegen.mts` wrote the lock at whatever `lock_filename` the response named, while the check has always opened `codegen.lock` by name. Since a lock is not a stampable artifact, the tree cleanup never removes it, so a rename would have left the old lock in place for the check to keep validating — green, from the wrong file. The writer now refuses a lock under any other name, reporting it per method and writing nothing, so the two agree by construction rather than by comment. This also validates the one response field that reached `path.join` unchecked; the `artifacts[]` paths were already covered by the SDK's own path validation inside the pre-write self-check.
- **The README's "File & image inputs" section documented code deleted in v0.3.0.** It still described the pre-`prepareInputs` flow — a `buildDocumentInput` wrapper that no longer exists anywhere in `src/` and an API-side data-URL decode that no longer happens. It now matches the actual flow: validate the data URL server-side, hand it to `client.prepareInputs()`, and run against the `pipelex-storage://` reference it returns.
- **`make use-npm` restored a stale version instead of the current one.** The target ran `npm install @pipelex/sdk`, which re-resolves the range already declared in `package.json` rather than fetching the current release. Because `@pipelex/sdk` is pre-1.0, a caret range never crosses a minor — so returning from a `make use-local` session with an out-of-date range reinstalled that range's newest match and called it "restored", silently **downgrading** the SDK. It now installs `@pipelex/sdk@latest`, which fetches the published release and re-pins the range to it, and it echoes the version it actually restored so the result is visible rather than assumed.

### Security

- **Bumped `next` to `^16.3.1`** (was `^16.2.9`), clearing every high-severity advisory `npm audit --omit=dev` reported against this template's production dependency tree. All of them came in through Next.js: a set of Next.js advisories of its own (Server Action denial of service and unbounded Edge-runtime payloads, SSRF via rewrites and on custom servers, cache confusion of response bodies, Image Optimization denial of service on SVGs, unauthenticated disclosure of internal Server Function endpoints, and a Turbopack middleware bypass), plus its pinned transitives — `postcss` (arbitrary `.map` file disclosure via an attacker-controlled `sourceMappingURL`, and XSS through unescaped `</style>` in stringify output), `nanoid` (non-terminating generator loops), and `sharp` (inherited libvips CVEs). Next `16.3.1` pins `postcss` `8.5.23` and `sharp` `^0.35.3`, which is what moves the whole tree onto patched versions; `16.2.12`, the highest remaining `16.2.x`, still carries `postcss` `8.4.31` and does not fix them. `eslint-config-next` was raised to `^16.3.1` alongside it to keep the linter in lockstep with the framework.
- **Bumped the `postcss` dev dependency to `^8.5.23`** and refreshed `brace-expansion` and `js-yaml` in the lockfile, so the full `npm audit` — development dependencies included — is now clean as well.

## [v0.3.0] - 2026-07-22

### Added

- **Cost Reports (`tokens_usages`)**: Added token usage and cost tracking for both blocking and durable runs, surfaced via a new `<CostReport>` component (rendered across the Entity, Image, and PDF example forms) that breaks down per-call token usage, model types, and computed USD costs. Backed by new `src/lib/usageReport.ts` utilities that parse and project raw `tokens_usages` and `usage_assembly_error` data into a render-ready format.
- **Upload Error Handling**: Added an `upload_failed` error kind in `src/lib/errors.ts` to classify SDK `InputPreparationError`s (e.g., `UnsupportedUploadCapabilityError`, `RejectedAssetError`, `UploadAuthenticationError`) with actionable, user-friendly UI messages.

### Changed

- **Cleaner File Uploads (Breaking)**: Replaced the hand-rolled base64 `Document` envelope in the PDF summarization pipeline with the SDK's `client.prepareInputs()`. Files now upload directly to Pipelex storage and pass to the run as lightweight `pipelex-storage://` URIs. This removes `buildDocumentInput` and `DocumentInput` from `src/lib/fileEncoding.ts` (pre-flight size and MIME validation remains intact).
- **Improved Polling Status UI**: Refactored the `useRun` hook and `<RunStatus>` component to replace the generic `degraded` boolean with a descriptive `health` state (`"reconnecting"` or `"retrying"`), providing cause-specific copy during transient network blips or server reconnects.
- **Development Port**: Changed the default local development and Playwright testing port from `3000` to `4100` (`package.json`, `README.md`, `playwright.config.ts`).
- **Dependencies**: Bumped `@pipelex/sdk` from `0.3.1` to `^0.5.1` (through `0.4.0` and `0.5.0`). `0.4.0`'s breaking changes are scoped to the `/v1/build/*` and tools routes this repo doesn't call; `0.5.0` delivered the typed `tokens_usages` and `prepareInputs` upload surface the two features above build on.
- **Testing**: Updated action-layer tests to use `toMatchObject` instead of `toEqual` to accommodate the new `usage` sibling property in run outcomes.

### Security

- **SDK Dependency Patch**: The final `0.5.1` hop inherits a patch for a transitive **dev** dependency (`brace-expansion`, CVE-2026-13149) in the SDK's own lockfile. That dependency is never shipped in the SDK's runtime surface, so no code changes were required here.

## [v0.2.0] - 2026-07-05

### Changed

- Breaking: swapped the Pipelex SDK from `mthds` (`MthdsApiClient`) to `@pipelex/sdk` (`PipelexApiClient`). `PipelexApiClient` reads `PIPELEX_API_KEY` / `PIPELEX_BASE_URL` natively, so the client is constructed bare with no env-var bridging. Error classes are imported from the `@pipelex/sdk` barrel (it has no `/errors` subpath; the barrel is client-bundle-safe).
- Breaking: renamed the env var `PIPELEX_API_URL` to `PIPELEX_BASE_URL` for consistency with the SDK's `baseUrl` naming. There is no read alias — update `.env.local` / your environment.
- `make use-local` / `make use-npm` now target the sibling `../pipelex-sdk-js` repo instead of `../mthds-js`.
- Bumped `@pipelex/sdk` to `0.2.0` (was `0.1.5`). No code changes needed for the `0.2.0` breaking renames (constructor option `apiToken` → `apiKey`, env var `PIPELEX_API_URL` → `PIPELEX_BASE_URL`): this repo constructs `PipelexApiClient` bare and already used `PIPELEX_BASE_URL`.
- Bumped `@pipelex/sdk` to `0.2.1` (was `0.2.0`), which makes the ESM-only SDK loadable from CommonJS (`default` export condition). The e2e specs now import `DEFAULT_API_BASE_URL` from the SDK directly instead of mirroring it as a local constant in `e2e/liveApi.ts`.
- Raised the minimum Node.js to 22.12 (`engines.node: ">=22.12.0"`, was `>=22`), matching the SDK's new floor: Playwright loads the e2e specs via CommonJS `require()`, and `require(esm)` is only unflagged from Node 22.12.
- Bumped `@pipelex/sdk` to `0.3.0` — one resolved output accessor across both execution modes. `RunResults.main_stuff` is now required (non-null), and the blocking `execute()` returns a `PipelexExecuteResult` whose `.main_stuff` the SDK resolves out of the working memory (via the response's `main_stuff_name`). `executeBlockingRun` therefore adapts the blocking response onto `RunResults` as `{ pipeline_run_id, main_stuff }`, and `findOutputContent` reads only `main_stuff` — the `pipe_output` working-memory search arm is gone, so both modes narrow the same resolved field.

### Fixed

- Blocking and durable modes now agree on which output is the "main" one. Previously the blocking path dropped the server's `main_stuff_name` and had `findOutputContent` guess the main output by predicate-shape-matching the first working-memory entry, so a pipeline with an intermediate stuff matching the same narrower predicate could render the wrong result in blocking mode while durable mode read the true `main_stuff` and was correct. With the SDK resolving `.main_stuff` on both paths, the shape-guessing is gone and the two modes can't disagree (closes the latent finding tracked in `wip/durable-runs-review-followups.md` #6).
